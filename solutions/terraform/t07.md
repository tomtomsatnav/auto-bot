# T07 solution: Refactor without destroying

## What's happening
Terraform tracks resources by **address**. The refactor changed every address:

| Old address (in state) | New address (in code) |
|---|---|
| `random_pet.server_name` | `random_pet.name` |
| `local_file.api` | `local_file.service["api"]` |
| `local_file.worker` | `local_file.service["worker"]` |

Terraform doesn't know they're the same things, so it plans to destroy the old addresses and create the new ones. The new `random_pet` gets a new random name, which then changes both files.

## Fix: `moved` blocks
Add these to `main.tf`:
```hcl
moved {
  from = random_pet.server_name
  to   = random_pet.name
}

moved {
  from = local_file.api
  to   = local_file.service["api"]
}

moved {
  from = local_file.worker
  to   = local_file.service["worker"]
}
```
Now `terraform plan` shows `has moved to` for each one, and **0 to add, 0 to change, 0 to destroy**. The file contents are identical because `"${each.key} on ..."` produces the same text as before.

## The older way
`terraform state mv 'local_file.api' 'local_file.service["api"]'` does the same thing, but it's a manual command that isn't reviewed in a pull request. `moved` blocks live in code, so they're reviewable, repeatable across environments and visible in the plan. Prefer them. (You can remove them later once every environment has applied.)

## Say this in the interview
- "Before applying anything, I read the plan summary line. Any destroy on a stateful resource is a red flag worth stopping for."
- "Renames in Terraform are a state problem, not a code problem. `moved` blocks tell Terraform it's the same resource with a new address."
