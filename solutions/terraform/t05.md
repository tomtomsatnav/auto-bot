# T05 solution: AWS networking

## Bug 1: `azs` has type `string`, but a list default (validate)
```
Error: Invalid default value for variable
This default value is not compatible with the variable's type constraint: string required.
```
**Fix:** `type = list(string)`

## Bug 2: `vpc_id = aws_vpc.main` (validate)
That's the whole VPC object, not its ID. **Fix:** `aws_vpc.main.id`

## Bug 3: association without an index (validate)
`aws_subnet.public` is a list because of `count`. **Fix:** `aws_subnet.public[count.index].id`

## Bug 4: overlapping subnet CIDRs (plan passes, apply fails)
In `terraform console`:
```
> cidrsubnet("10.0.0.0/16", 8, 0)
"10.0.0.0/24"
> cidrsubnet("10.0.0.0/16", 8, 1)
"10.0.1.0/24"
```
Public and private **both** use `count.index`, so both get `10.0.0.0/24` and `10.0.1.0/24`. AWS would reject the second subnet with a CIDR conflict error.

**Fix:** offset the private range:
```hcl
cidr_block = cidrsubnet(var.vpc_cidr, 8, count.index + 10)   # 10.0.10.0/24, 10.0.11.0/24
```

## Bug 5 (security): database open to the internet
`cidr_blocks = ["0.0.0.0/0"]` on port 5432 means the whole internet can reach Postgres. The brief said "only the application".

**Best fix:** reference the application's security group:
```hcl
ingress {
  description     = "Postgres from app servers"
  from_port       = 5432
  to_port         = 5432
  protocol        = "tcp"
  security_groups = [aws_security_group.app.id]
}
```
(With no app security group in this config, `cidr_blocks = [var.vpc_cidr]` is an acceptable minimum, but mention that a security group reference is tighter.)

## Say this in the interview
- "Let me sketch the network first: VPC, two public subnets with a route to the internet gateway, two private subnets, and a database security group."
- "I'll use `terraform console` to evaluate the CIDR functions rather than doing the maths in my head."
- "Referencing security groups rather than IP ranges is better practice, because it follows the resources rather than addresses."
