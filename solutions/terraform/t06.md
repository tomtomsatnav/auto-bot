# T06 solution: AWS IAM

## Bug 1: missing `.json` (validate)
`assume_role_policy` wants a JSON **string**, but `data.aws_iam_policy_document.assume` is an object.
**Fix:** `assume_role_policy = data.aws_iam_policy_document.assume.json`

## Bug 2: attachment uses the role ARN (fails on apply)
`aws_iam_role_policy_attachment.role` expects the role **name**. The docs say so, but plan doesn't check it.
**Fix:** `role = aws_iam_role.task.name`

## Bug 3: `GetObject` on the bucket ARN (works on apply, fails at runtime)
- `s3:ListBucket` applies to the **bucket**: `arn:aws:s3:::name`
- `s3:GetObject` applies to **objects**: `arn:aws:s3:::name/*`

As written, the service can list files but gets `AccessDenied` when reading them. This is sneaky because Terraform succeeds and the bug only shows up at runtime.

**Fix:** split the statements:
```hcl
statement {
  sid       = "ListArtifactsBucket"
  actions   = ["s3:ListBucket"]
  resources = [var.bucket_arn]
}

statement {
  sid       = "ReadArtifactObjects"
  actions   = ["s3:GetObject"]
  resources = ["${var.bucket_arn}/*"]
}
```

## Bug 4 (security): `s3:*` on `*`
"Temporary debug access" gives full control of **every bucket in the account**: read, write, delete, change policies. It completely undoes the least-privilege intent. **Remove the statement.** Temporary access is still access: if debugging needs it, grant it separately and time-limit it.

## Say this in the interview
- "IAM bugs often pass plan and even apply. They show up as `AccessDenied` at runtime, so I read policies against what the service actually needs."
- "Bucket-level and object-level actions need different resource ARNs. That's one of the most common S3 IAM mistakes."
- (This is your security background showing, so use it.) "I'd flag the wildcard statement as a blocker in review, whatever the name says."
