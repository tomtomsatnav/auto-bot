# D04 solution: Permissions

## Bug: `appuser` can't write to `/app`

`WORKDIR /app` runs while the user is still root, so `/app` is owned by root. After `USER appuser`, the app tries `mkdir /app/data/uploads`:
```
PermissionError: [Errno 13] Permission denied: '/app/data'
```

**Fix:** create the writable directory and hand it to `appuser` **before** switching user:
```dockerfile
FROM python:3.12-slim

RUN useradd --create-home --uid 10001 appuser

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY main.py .

RUN mkdir -p /app/data/uploads && chown -R appuser:appuser /app/data

USER appuser

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```
Only the data folder is made writable. The code stays owned by root, so a compromised app can't modify itself. That's a good point to mention.

## Why deleting `USER` is the wrong fix

Running as root means that if an attacker exploits the app, they're root inside the container, making container escapes and lateral movement much easier. It fixes the symptom by removing a security control.

## Stretch: persistence

The container's filesystem is thrown away when it's removed. Use a named volume:
```bash
docker volume create d04-data
docker run -d --name d04 -p 8000:8000 -v d04-data:/app/data d04
```
When a fresh, empty named volume is mounted over a directory that exists in the image, Docker copies that directory's contents **and ownership** into it, which is why the `chown` in the Dockerfile matters.

## Say this in the interview
- "`docker ps -a` shows it exited, so I'll check `docker logs` for the reason."
- "I'd rather fix the permissions than remove the non-root user. Least privilege is the whole point of that change."
